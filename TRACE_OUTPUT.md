# kodiag Trace Log — Format & Retrieval

The main coding LLM reads trace output directly off disk when it needs to inspect a program's call flow (arguments, return values, errors, timing). This file documents everything needed to find and interpret that output.

## What produces output

Output is generated by the `trace` decorator (`kodiag.trace`, defined in `src/kodiag/decorators.py`) when it is called **with a `file_name`**:

```python
from kodiag import trace

@trace("file_name", precision=3)
def some_function(...):
    ...
```

- `file_name` (str, required to enable file output): base name for the trace. The `.html` extension is appended automatically if not already present (e.g. `"orders"` → key `"orders.html"`).
- `precision` (int, default `3`): number of decimal places `elapsed` is rounded to.
- If `trace()` is called with no `file_name` (or `file_name=None`), nothing is written to disk — calls are only printed to stdout. See README.md for that mode.

Every function decorated with the **same `file_name`** shares one call list, appended to in call order. This is how a multi-function flow ends up as a single trace.

Output is only flushed to disk **at interpreter exit** (registered via `atexit`), not after each call. If the process is killed (not a normal exit), the file is not written. Writing is idempotent per-process (`_closed` flag) — `atexit` runs the write once.

## Output file paths

For `@trace("orders")` (or `@trace("orders.html")`), on process exit kodiag writes two files under `kodiag_output/<name>/`, where `<name>` is the file_name with any `.html` suffix stripped:

```
kodiag_output/orders/orders.html   ← interactive HTML diagram
kodiag_output/orders/orders.md     ← Markdown trace table
```

Both paths are relative to the process's current working directory at exit. `kodiag_output/` is created automatically if missing.

**To find trace output for a run**: look in `kodiag_output/<file_name>/<file_name>.md` first — it's the cheap, token-efficient read. Only open the `.html` file if you need the visual diagram itself.

## Markdown output spec (`kodiag_output/<name>/<name>.md`)

Fixed table schema, one row per recorded call, in call order:

```
# Trace Log

| # | Function | Args | Kwargs | Result | Error | Elapsed |
|---|----------|------|--------|--------|-------|---------|
| `1` | `fetch` | `[42]` | `{}` | `{"id": 42}` | `null` | `0.012s` |
| `2` | `process` | `[{"id": 42}]` | `{}` | `null` | `"missing 'name'"` | `0.001s` |

**Flow:** `fetch` → `process*`
```

- `#`: 1-indexed call order within this file_name.
- Every cell in a data row is wrapped in backticks (the header/separator rows are not). Any literal `|` in a value is backslash-escaped so it can't break the columns.
- `Function`: the decorated function's `__name__`.
- `Args` / `Kwargs`: JSON-serialized positional/keyword arguments as received by the call.
- `Result`: JSON-serialized return value. `null` if the call raised (see below) or if it returned `None`.
- `Error`: JSON-serialized `str(exception)` if the call raised, else `null`. This is only the exception's message — the exception type name is **not** included (e.g. `KeyError('name')` is recorded as `"'name'"`, not `"KeyError: 'name'"`).
- `Elapsed`: seconds, rounded to `precision` decimal places, suffixed `s`.
- **Flow** line: space-arrow-joined function names in call order; a call that raised is suffixed with `*` (e.g. `` `process*` ``).

**Result and Error are recorded as separate columns.** When a call raises, `Result` is always `null` (the decorator records the value the wrapper held, and the return value is never assigned once the function raises) and `Error` holds the exception string; the original exception is then re-raised to the caller. A `null` result therefore means either the call returned `None` or it raised — check the `Error` column (and the `*` in the Flow line) to tell the two apart.

When scanning this file for a main agent's benefit: always report the full **Flow** line first, then surface the highest-signal rows — anything with a non-null `Error`, and the rows with the largest `Elapsed` — rather than dumping the whole table.

## HTML output spec (`kodiag_output/<name>/<name>.html`)

Same call data, rendered as a horizontal chain of cards (one per call, connected by arrows) for human viewing in a browser. On a card for a call that raised, the `→ error:` line is colored red; the card border itself is unchanged. A fixed bottom bar offers:

- **Copy Mermaid** — copies a `flowchart LR` version of the flow to the clipboard (error nodes get `style nN color:red`).
- **Download Draw.io** — downloads the flow as an XML file, always named `trace.drawio` regardless of `file_name` (error nodes get `fontColor=red; stroke=#cc3`).
- **Print / Save PDF** — opens the browser print dialog (the export bar itself is hidden in print/PDF output).

The Mermaid and Draw.io labels show the same `elapsed` value as the `.md` table — already rounded to `precision` when the trace was recorded.

There is no Markdown-copy button in the HTML — Markdown is only available as the separate `.md` file described above, not as a UI export from the diagram page.

This file is for human/browser consumption; the coding agent should read the `.md` file for programmatic inspection.

## Practical notes for the agent

- Multiple runs of the same program with the same `file_name` overwrite the previous `kodiag_output/<name>/` contents — there is no history/versioning.
- If `kodiag_output/<name>/` doesn't exist, either the program hasn't exited normally yet, no function with that `file_name` was ever called, or a different `file_name` was used than expected — check the `@trace(...)` call sites (`grep -rn '@trace(' `) to confirm the exact name in use.
- `kodiag_output/` is a generated artifact directory, not source — don't treat its contents as hand-authored or edit it directly.
